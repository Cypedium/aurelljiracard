# CLAUDE.md

Project-specific instructions for Aurell Jira Board. Where this file is more specific than a parent CLAUDE.md (folder layout, module system, response shape, branch names), this file wins.

## Branch check — do this first

Before changing any file for a new **feature**, **bug** or **fix** request (in English or Swedish, e.g. "lägg till", "fixa", "buggen"):

1. Run `git branch --show-current` and `git status --short`.
2. **On `main`** → create a branch before editing anything:
   ```bash
   git pull --ff-only
   git switch -c feature/<short-kebab-desc>   # new feature or improvement
   git switch -c fix/<short-kebab-desc>       # bug or fix
   ```
   For non-code work (docs, config, CLAUDE.md) use `docs/<desc>` or `chore/<desc>`. Tell the user the branch name in one line.
3. **On another branch** → if the request continues that branch's work (the user says "on the same branch", or it is a follow-up to it), stay. If it is unrelated, or the branch is already merged (`git branch --merged main` lists it), ask whether to start a new branch from `main`.
4. **Uncommitted changes** → leave the known local edit to `server/.env` alone (never stage it). Anything else: ask before switching branches.
5. Re-check the branch before every commit — the user may have switched or merged in between. Never commit, push or merge to `main`.

## Layout

Two independent npm projects plus a Maven project — always `cd` into one before running npm or `./mvnw`. There is no root `package.json`.

- `server/` — Express 5 + Mongoose 9, **CommonJS** (`require`/`module.exports`), entry `server.js` (DB connect + listen), `app.js` (Express app, exported for tests)
  - `routes/` → `controllers/` → `models/`; `middleware/authMiddleware.js`, `middleware/boardAccess.js` (`requireMember` → `req.boardId`/`req.boardRole`, `requireBoardAdmin`); `utils/jwt.js`, `utils/validate.js`
  - `routes/board.js` mounts `card`, `column`, `issue-type` under `/board/:boardId` after `auth` + `requireMember`; `routes/invite.js` is `POST /invite/:token`
  - `tests/` — Jest + Supertest; models are `jest.mock`ed, no DB
  - `backupfiles/`, `scripts/` — one-off seed/maintenance scripts, not part of the app (`scripts/migrateBoards.js`: the Mongo version of V11, run by hand before deploying boards)
- `frontend/` — Next.js 16 App Router, React 19, TypeScript, Tailwind 4 + CSS modules
  - `app/api/api.ts` — axios instance (attaches token, refreshes on 401 — except for `/auth/*`, where 401 means bad credentials); `app/api/endpoints.ts` — all API calls
  - `app/cards/Cards.tsx` — board: `react-grid-layout` v2, fixed columns To Do / In Progress / Test / Done, width from `useContainerWidth`
  - `app/cards/card/Card.tsx` — create form (Jira "create issue" style)
  - `app/utils/boardLayout.ts` — board columns and card placement (pure, unit-tested)
  - `app/cards/useBoards.ts` — the user's boards (`GET /board`) and the one shown (`current`, `boardAdmin`), shared by the navbar and pages; `selectBoard` (navbar `BoardSwitcher`), `showJoinedBoard`, `reloadBoards`. The choice is kept in `localStorage` (`CURRENT_BOARD_KEY`); an invite opened before login is kept in `sessionStorage` (`PENDING_INVITE_KEY`) and accepted on the next load. Pure helpers in `app/utils/currentBoard.ts`. Every board-scoped endpoint takes `boardId` first; components read it from `useBoards().current`, and `Cards.tsx` remounts the board with `key={boardId}` on a switch
  - Board role gating: `boardAdmin` (owner) for lists, issue types, Share and editing any card; the global `isAdmin()` only for the Users page. `ShareBoardDialog` (navbar "Share"/"Members", `BOARD_ACTIONS.shareBoard`): invite link, members, remove/leave. `app/invite/[token]/page.tsx` joins a board
  - `app/cards/useIssueTypes.ts` — the current board's issue types (`GET /board/:id/issue-type`, fetched once per board, defaults until then); `addIssueType` after an admin creates one in `NewIssueTypeDialog` (opened from "New issue type" in `IssueTypeSelect` or from "Create Issue type" in the navbar on the admin page `app/issue-types/`, via `BOARD_ACTIONS.createIssueType`), `removeIssueType` after one is deleted there. Pure helpers and defaults in `app/utils/cardType.ts`
  - Module-level constants belong in `app/utils/` (domain file, e.g. `cardForm.ts`, `styles.ts`), not in components
  - `app/components/` — `Layout`, `Navbar`, `Footer`, login/register forms
  - Account menu: the navbar avatar opens `AccountMenu` (Trello-style popover: Account with "Google sign-in", Aurello with "Board background"/"Navbar colour", Log out — there is no Logout link in the navbar any more). Its items open a panel left of the menu on desktop and in place of it on mobile (back arrow, `PanelHeader`)
  - Appearance: `AppearancePicker.tsx` (from the account menu) picks the board background (gradients, colours or any custom `#rrggbb`) and a navbar theme (greys or colours, two shades: top row, darker second row; or a custom colour, second row shaded by `mixHex`). `Appearance` values are a preset key or a lowercase hex. Saved per browser (`localStorage` `appearance`, `app/utils/appearanceStore.ts`) and applied as CSS variables on `<html>` (`--color-board-from/via/to`, `--color-nav-top/sub/text`; defaults in `app/root.css` must match `DEFAULT_APPEARANCE`). The navbar text takes the background's `text` colour unless its contrast with the navbar is below 3 (`navbarTextColor`). Data and rules in `app/utils/appearance.ts` (pure, unit-tested)
  - Google sign-in: `GoogleButton` (Google Identity Services script loaded by `app/utils/google.ts`, no npm package; renders nothing without `NEXT_PUBLIC_GOOGLE_CLIENT_ID`) on the login form → `POST /auth/google`; "Google sign-in" in the account menu connects Google to a password account → `POST /user/google`
  - `app/components/ui/` — shadcn/ui components (`dialog`, `alert-dialog`, `button`, `sonner`, `select`, `input`, `label`, `textarea`, `form`), added with `npx shadcn@latest add <name>` (config: `components.json`). Owned code: edit freely, but keep `z-[1001]` on dialog overlays (Navbar is `z-[1000]`) and `z-[1002]` on `SelectContent` (it opens inside dialogs). `cn()` lives in `app/lib/utils.ts` — check new components import it from there, not from an npm package
  - Forms use react-hook-form + zod via shadcn `Form` (`FormField` → `FormItem` → `FormLabel`/`FormControl`/`FormMessage`), with `zodResolver` and `noValidate` on the `<form>`. Schemas live in `app/utils/` (`cardForm.ts`, `register.ts`) and are unit-tested; keep their limits and messages in sync with the backend controllers. Don't trim usernames (the backend stores them as typed). Field errors stay inline (`FormMessage`)
  - Styling: `LABEL_CLASS`, `FORM_ITEM_CLASS`, `FIELD_ERROR_CLASS`, `AUTH_FORM_CLASS` from `app/utils/styles.ts`. When `shadcn add` asks to overwrite an existing file, answer no (`yes n | npx shadcn@latest add <name>`)
  - Use `Dialog`/`AlertDialog` for modals and confirmations and `toast` from `sonner` for messages — never `alert`/`confirm`. `<Toaster richColors closeButton />` is in `client-layout.tsx`
  - Request/server errors → `toast.error(apiErrorMessage(err, "<fallback>"))` (`app/utils/apiError.ts` reads the backend's `{ message }`), not an inline error box. Repeating background errors get a fixed `id` so they replace each other. Log `err.message` only — a full axios error includes the `Authorization` header
  - Import alias `@/*` → `frontend/*` (used by `components/ui`; app code uses relative imports)
  - `tests/unit/` — Jest via `next/jest`; import test globals from `@jest/globals`
- `server-java/` — Spring Boot 4.1 + PostgreSQL port of `server/`, Java 25, Maven wrapper. Package `se.aurell.jiraboard` under `src/main/java/`:
  - `controller/` — `AuthController` (`/auth`), `BoardController` (`/board`, `/board/{boardId}/invite|member`, `/invite/{token}`), `CardController` (`/board/{boardId}/card`), `ColumnController` (`/board/{boardId}/column`), `IssueTypeController` (`/board/{boardId}/issue-type`), `UserController` (`/user`), `HealthController` (`/health`). Thin: `@Valid @RequestBody`, `@PathVariable UUID boardId`, `@AuthenticationPrincipal AuthUser`, delegate to a service
  - `service/` — business rules, `@Transactional` (reads `readOnly = true`). `BoardService.requireMember` (404 "Board not found.") / `requireAdmin` (403 "Board admins only.") are called first in every board-scoped service method; `createFor(userId)` makes a new user's board (register, first Google sign-in); `CardService.findEditableCard` (author or board admin, else 403)
  - `repository/` — Spring Data JPA; `UserRepository.revokeTokens` is the atomic logout revoke (also sets `loggedOutAt`)
  - `entity/` — `User`, `Board`, `BoardMember`, `Card`, `BoardColumn` and `IssueType` (composite `@IdClass` keys with `boardId`), `CardType` (default types, icon list, key helper), `CardStatus` (default lists, constants, list-key helpers), `Layout` record stored as `JSONB`
  - `dto/` — request/response records; validation via Bean Validation annotations whose messages match the Express API. Responses use `@JsonProperty("_id")` for ids
  - `security/` — `@AdminOnly` (`@PreAuthorize("hasRole('ADMIN')")`, the global site admin; only the `/user` admin methods use it, `AdminOnlyApiTest` lists them; denial → 403 "Admins only." in `GlobalExceptionHandler`. Board rights are not here, see `BoardService`), `JwtService` (Nimbus HS256 encode/decode), `AccessTokenConverter` (token → `AuthUser` + `ROLE_<role>` authority), `ApiBearerTokenResolver` (ignores `Authorization` on `/auth/**` and `/health`), `JsonAuthenticationEntryPoint` (401 `{ message }`)
  - `config/` — `SecurityConfig` (stateless filter chain, CORS, BCrypt strength 10 so hashes match `server/`), `JwtProperties`, `CorsProperties`
  - `exception/` — throw `ApiException.badRequest/unauthorized/forbidden/notFound/conflict(...)`; `GlobalExceptionHandler` maps everything to `{ message }`
  - `src/main/resources/application.yml` — all config read from env vars; `db/migration/V1__init.sql` — `users` and `cards` tables
  - `src/test/` — `ApiIntegrationTest` base (`@SpringBootTest` + MockMvc + Testcontainers `postgres:17-alpine`, profile `dev`, wipes users and cards before each test — boards cascade; helpers `boardId(token)`, `joinBoard(owner, member)`, `on(board, path)`); subclasses `AuthApiTest`, `BoardApiTest`, `CardApiTest`, `ColumnApiTest`, `IssueTypeApiTest`, `UserApiTest`, `BoardMigrationTest` (runs V10 → V11 on seeded data in a separate schema); `security/JwtServiceTest`. `TestJiraboardApplication` runs the app locally against a throwaway container
  - Must stay API-compatible with `server/` (paths, `_id`, `{ message }` errors, status codes, token rules); change both together. Known differences: UUID ids, `400 "Invalid request body."` for malformed JSON/wrong field types, and Google sign-in (`POST /auth/google`, `POST /user/google`, `security/GoogleTokenVerifier`) exists only here (see `server-java/README.md`)
  - Schema only via Flyway (`src/main/resources/db/migration/V<n>__*.sql`); Hibernate runs `ddl-auto: validate`. Never edit an applied migration
  - Tests use Testcontainers — Docker must be running. Dev-only secrets live in `src/test/resources/application-dev.yml`
- `docs/backend-map.html` — standalone interactive map of `server-java` (endpoint data is hand-written in its `<script>`); update it when endpoints, services, repositories or tables change
- `PythonTests/` — manual smoke scripts against a running API (create real data; not run in CI)

`frontend/app/node_modules/` is a stray install — exclude it (and every `node_modules`) from searches.

## Conventions

- **API paths**: backend mounts `/auth`, `/board`, `/invite`, `/user` (`server-java` also has a public `GET /health`). Cards, lists and issue types are under `/board/:boardId/card|column|issue-type`; there are no global `/card`, `/column`, `/issue-type` routes any more. Frontend calls go through `endpoints.ts`, and `tests/unit/endpoints.test.ts` pins every path — update both together.
- **Responses**: success returns the resource or `{ message }`; errors return `{ message }` with a proper status (`400` validation, `401` missing/expired token, `403` forbidden, `404`, `409`). Do not switch to a `{ success, data }` envelope without migrating the frontend in the same change.
- **Boards**: every user owns one board and is its admin (board role `admin`); others join through an invite link as collaborators (`user`). Membership and board role are read from the database per request (`BoardMember` / `board_members`), never from the token or body. Non-members get `404 "Board not found."` (don't reveal the board), members without rights `403 "Board admins only."`. The global `User.role` admin only manages users and gives no rights on boards.
- **Auth**: every non-`/auth` route uses `authMiddleware`. Identity (`req.user.id`, `req.user.username`) comes from the token — never trust `username`/`userId` in the request body. Expired access tokens must return `401` (the frontend only refreshes on 401).
  - Java: `SecurityConfig` permits `/auth/**`, `/health`, `/error`; everything else is `authenticated()`. Get identity from `@AuthenticationPrincipal AuthUser` (`id`, `username`), never from a DTO field.
- **Tokens**: access 15m (`JWT_SECRET`, payload `{ id, username, role }`), refresh 7d (`REFRESH_SECRET`, payload `{ id, tokenVersion }` + `jti`). Logout increments `User.tokenVersion` to revoke all refresh tokens. Refresh tokens are single-use: each `jti` is a `RefreshToken` (Mongo, TTL index) / `refresh_tokens` row (Postgres `V9__refresh_tokens.sql`); a login starts a family, `/auth/refresh` marks the token used and issues the next one in the family, and a used token that comes back deletes the whole family (that login only) with `403 "Invalid refresh token"`. Tokens without a `jti` (issued before V9) are accepted once, keyed by a hash of the token — `legacyToken`/`legacyTokenId`, to be removed 7 days after the deploy. Frontend stores tokens and `username` in `sessionStorage` (`SESSION_KEYS` in `app/utils/session.ts`), so closing the window/tab logs the user out while a reload keeps them in; board preferences (`user_layout`, collapsed lists) stay in `localStorage`.
- **Validation**: validate type and length of every body field in the controller (see `utils/validate.js`) before touching the DB. `mongoose.set('sanitizeFilter', true)` is on; still never pass raw objects from `req.body` into queries.
  - Java: Bean Validation annotations on the request record (`@NotBlank`, `@Size`, `@Min`/`@Max`) with the same messages as `server/`; checks that annotations can't express (password byte length, picture URL, card status) go in the service as `ApiException.badRequest`. Unknown `type` values are rejected by `IssueTypeService.requireCardType`; `status` by `ColumnService.requireCardStatus`.
- **Logging**: never log tokens, passwords, `MONGO_URI` or full request bodies. Log `err.message` in controllers. Java: only `GlobalExceptionHandler` logs unexpected errors (type + message); return expected errors by throwing `ApiException`, not by building `ResponseEntity`s in controllers.
- **UI style**: board and forms follow Jira's look (colours `#172b4d` text, `#44546f` secondary, `#0c66e4` primary, `#f1f2f4` lanes). Reuse these in new UI. shadcn tokens (`--primary`, `--border`, `--ring` …) in `app/root.css` are mapped to these colours; there is no dark mode (`dark:` only applies under a `.dark` class). Portaled content (dialogs, toasts) needs `font-jira` itself.
- Comments in the codebase mix Swedish and English; either is fine, keep new ones short.

## Config and secrets

- `server/.env` is listed for ignore but **is still tracked in git** — never stage or commit it, and don't print its contents. Template: `server/.env.example`. Production secrets live in `fly secrets` for `aurelljiraboard-backend` and `aurelljiraboardjava`.
- `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_GOOGLE_CLIENT_ID` (optional) are inlined at build time: `.env.local` locally, `[build.args]` in `frontend/fly.app.toml` for production (`Dockerfile.app` passes both through).
- CORS origins: `CLIENT_URL` (comma-separated) in `server/app.js` and `app.cors.allowed-origins` in `server-java/src/main/resources/application.yml`.
- `server-java` reads env vars only (Spring does not load `.env`): `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`, `REFRESH_SECRET` (each ≥32 bytes, app refuses to start otherwise), `PORT` (default 8080), `CLIENT_URL`, `GOOGLE_CLIENT_ID` (optional, the public OAuth client id; empty = Google endpoints answer `503`). Template: `server-java/.env.example`. Never put real secrets in `application*.yml`.
- Never commit `.env*` files, credentials, tokens, or curl snippets containing them. Stage files by name, never `git add -A` / `git add .`.

## Deployment

Pushes to `main` deploy both Fly apps after CI passes (`fly.server.toml`, `fly.app.toml`, region `arn`). Changing Dockerfiles, Fly configs or workflows affects production — call it out in the PR. `server-java` is deployed by hand as Fly app `aurelljiraboardjava` (`fly deploy -c fly.java.toml` in `server-java/`, `Dockerfile.java`, external PostgreSQL via `DB_URL`); CI runs its tests (job `server-java`, which also gates the Fly deploys) but does not deploy it. The production frontend (`fly.app.toml` `NEXT_PUBLIC_API_URL`) points at `aurelljiraboardjava`, so deploy `server-java` before a change that needs it reaches `main`.

## Data model

- `User`: `username` (unique, case-insensitive in code: register/rename/login match any casing, stored as typed; no rude words — `server/utils/username.js`, `frontend/app/utils/username.ts`, Java `CredentialRules` share one list; new passwords 8–72 chars, no char 3× in a row, ≥4 distinct — `server/utils/password.js`), `passwordHash` (Postgres: `null` for users created by Google sign-in; password login refuses them), `googleSub`/`email` (Postgres only, `V10__google_login.sql`: Google's `sub`, `UNIQUE`; set on Google sign-in or when connecting Google; the first Google sign-in creates a user named after the email's local part, numbered if taken), `pictureUrl` (base64 data URL or http(s), ≤1.5 MB), `role` (`user` | `admin`, default `user`; the global site role: admins manage users via admin-only `PATCH`/`DELETE /user/:id` and `POST /user/:id/logout` (`server/middleware/requireAdmin.js`, Java `@AdminOnly` on the controller methods; an admin cannot delete themselves or drop their own admin role; users who author cards, or whose own board has cards, cannot be deleted (their board, its lists/types and memberships go with them); rename/role change bumps `tokenVersion`, and cards follow a rename — Mongo `updateMany`, Postgres `ON UPDATE CASCADE` from `V5__user_rename_cascade.sql`); the first admin is set in the database; lives in `server/utils/role.js`, must match `ROLES` in `frontend/app/utils/session.ts` and the Java `Role` enum, Postgres `CHECK` in `V3__user_role.sql`; tokens without a `role` claim read as `user`), `tokenVersion`, `lastActiveAt`/`loggedOutAt` (presence for the admin user list: set on login/refresh and on logout or admin logout; `GET /user` adds `lastActiveAt` and `online` for admins only — online = active within 20 min and not logged out since; `server/utils/presence.js` must match Java `AdminUserResponse.ONLINE_WINDOW`; Postgres `V7__user_presence.sql`), embedded `layout { cols, headers[], cards[] }` — one per user for all their boards (positions keyed by card id; the frontend keeps other boards' positions when saving, `mergeBoardPositions`); the board reads only `layout.cards`, for the order of cards within a list (`status` = list key, so the order survives lists being moved; older positions have only `x` = list index and get a `status` on the next save); `headers[]` is legacy and no longer sent by the frontend
- `Board` (Postgres `boards`, `V11__boards.sql`): `ownerId` (UNIQUE: one board per user, created on register/first Google sign-in in Java, lazily by `GET /board` in Mongo — `Board.ensureFor`), `inviteTokenHash` (SHA-256 hex of the invite token, UNIQUE, `null` = no link; the token itself is never stored). Name shown = `"<owner>'s board"` (computed, follows a rename)
- `BoardMember` (Postgres `board_members`): `boardId`, `userId` (unique pair), `role` (`admin` = the owner, `user` = collaborator). V11 / `scripts/migrateBoards.js` moved all pre-board data to the oldest admin's board and added every other user to it as a collaborator
- `Column` (Postgres `board_columns`): a board's lists, **shared by the board's members** — `boardId`, `key` (lowercase letters/digits with hyphens, made from the title on create, unique per board, never `backlog`), `title` (≤ 50), `color` (`#rrggbb` lowercase or `null` = default; `HEX_COLOR` must match in `server/controllers/columnController.js`, `server-java` `ColumnRequest`/`LayoutRequest` and `frontend/app/utils/color.ts`), `position`. Members read them (`GET /board/:id/column`); only the board admin adds (`POST`, max 12 per board), renames/recolours (`PUT …/column/:key`) and moves them (`PUT …/column` with `{ keys }`, every list once; the frontend drags the list header). The board admin deletes empty lists (`DELETE …/column/:key`, `409` while any card on the board has that status; `todo` is the default and can't be deleted — "Delete column" in the navbar opens `DeleteListDialog`, rule in `listDeleteBlocker`). The four defaults (`DEFAULT_COLUMNS` in `server/utils/cardStatus.js`, seeded per board on first read in Mongo; Java `CardStatus.DEFAULT_COLUMNS`, seeded by `BoardService.createFor` and for existing boards by V11) must match `DEFAULT_HEADERS` in `frontend/app/utils/boardLayout.ts`. Hiding a list is per browser (`collapsed_columns` in `localStorage`)
- `Card`: `boardId` (the board it is on; a card id with another board's id is "not found"), `rating` 1–5 (form: "Priority", board: estimate pill), `comment` ("Summary"), `productId` ("Issue key", unique per board, exact match: Mongo unique index `{ boardId, productId }` + `409 "Issue key already exists."`, Postgres `UNIQUE (board_id, product_id)` from V11), `username` (author), `assignee` (who works on it; `null` in the backlog, set to the caller when a card leaves the backlog, missing on older cards → shown as the author; Postgres column from `V4__backlog_assignee.sql`), `submittedAt` (set by the server on create, never changed), `type` (an `IssueType` key, default `task`; checked on create and update), `status` (a `Column` key on the card's board, or `backlog` — not on the board, listed on `/backlog`; checked against the board's columns on create and in `PATCH …/card/:id/status`, which any board member may call; unknown statuses on old cards show in the first list). `BACKLOG_STATUS` must match `frontend/app/utils/backlog.ts` and `CardStatus.BACKLOG`
- `IssueType` (Postgres `issue_types`): a board's issue types, **shared by the board's members** — `boardId`, `key` (made from the label like list keys, unique per board), `label` (≤ 30), `color` (`#rrggbb` lowercase, required), `icon` (one of `ISSUE_TYPE_ICONS` in `server/utils/cardType.js`, must match Java `CardType.ICONS` and `frontend/app/utils/cardType.ts`), `position`. Members read them (`GET /board/:id/issue-type`); only the board admin adds them (`POST`, max 12 per board) and deletes them (`DELETE …/issue-type/:key`, `409` while any card on the board uses it; `task` is the default and can't be deleted). No rename yet. The three defaults (`DEFAULT_ISSUE_TYPES` in `server/utils/cardType.js`, seeded per board on first read in Mongo; Java `CardType.DEFAULTS`, seeded with the board and by V11) must match the frontend defaults
- PostgreSQL (`server-java`): `users` (UUID `id`, `username` VARCHAR(32) UNIQUE, `password_hash` (nullable), `google_sub` UNIQUE, `email`, `picture_url` TEXT, `token_version`, `layout` JSONB, `created_at`/`updated_at`), `boards` (UUID `id`, `owner_id` FK → `users` UNIQUE `ON DELETE CASCADE`, `invite_token_hash` UNIQUE), `board_members` (PK `(board_id, user_id)`, both FK `ON DELETE CASCADE`, `role` `CHECK`), `cards` (UUID `id`, `board_id` FK → `boards` (no cascade), `CHECK` on `rating` 1–5, `status` and `type` VARCHAR(32) without `CHECK`/FK, `username` FK → `users.username`, `UNIQUE (board_id, product_id)`, index on `(board_id, submitted_at DESC)`) `board_columns` (PK `(board_id, column_key)`, `title`, `color`, `position`) `issue_types` (PK `(board_id, type_key)`, `label`, `color`, `icon`, `position`) and `refresh_tokens` (UUID `id` = jti, `family_id`, `user_id` FK → `users` `ON DELETE CASCADE`, `expires_at`, `used_at`). Adding a list or an issue type is data (`POST /board/:id/column`, `POST /board/:id/issue-type`); adding an icon means changing `server/utils/cardType.js`, `CardType.ICONS` and the frontend

Schema changes need the user's approval.
